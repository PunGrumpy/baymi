# Notes

Things that cost time to find out. Each one is why some line of this agent, or of its tooling, looks the way it does, kept here so the code does not have to hold the paragraph.

## eve

**The channel posts the turn's own message, so a comment tool posts a second one.** eve's GitHub channel installs a `message.completed` handler that posts any completed message into the thread the session is anchored to. A turn that answers by calling `github__addIssueComment` or `github__addPullRequestComment` is posted twice, once as the tool's comment and once as the reply narrating that it posted it. Every GitHub instruction here says the reply is the comment; the comment tools are for writing on some _other_ thread.

**The channel posts the review, not a tool.** `github__createPullRequestReview` exists in github-tools and takes `event` plus inline `comments[]`, but mounting it would mean either trusting the model with `APPROVE`/`REQUEST_CHANGES` (gateable on the payload) or posting twice, since the built-in `message.completed` handler posts the reply anyway. `agent/channels/github.ts` overrides that handler instead: the reply is parsed (`agent/lib/github/review.ts`) and submitted as one review with a fixed `COMMENT` event, and a reply that is not a review is posted as a comment the way the default did. GitHub answers 422 for an inline comment on a line outside the diff, and one bad line fails the whole review, so any failure falls back to a plain comment and logs the error rather than losing the findings. `splitComment` replaces eve's `splitGitHubCommentBody`, which is not exported.

**Vercel Agent's review format, read off two public pull requests (2026-09-11).** No summary comment. One review with `COMMENTED` state and an empty body, one inline comment per finding, one sentence each, a "Fix on Vercel" image link to a sandbox-validated patch, and hidden `<!-- VADE-… -->` markers for category, recommendation, head and base SHA, review id and task id. When a human disputes a finding it replies in the thread and marks `<!-- VADE-OUTCOME: ISSUE_RESOLVED -->`. Baymi copies the shape (inline, one line visible, markers for a second look) and not the button, because a button that looks validated over a patch nobody ran would be a lie; GitHub's native `suggestion` block is the honest equivalent. The body is the count line and nothing else. `anchorReview` cuts it to that line whatever the model wrote, because the skill alone did not hold: the review on chat-adapter-line#34 opened with two paragraphs describing the feature to its author. The `ai-sdk-factory` rubric on `vercel/ai#20792` (title, `Outcome:`, one `Risk:` section per concern) was tried for the body on 2026-09-16 and dropped the same day. It is a summary comment, which this shape exists to avoid.

**The model cannot count diff lines, so the channel anchors findings for it (2026-09-16).** The diff in context is a unified patch, so a `File: path:line` needs the new-side number computed from a hunk header by hand. On `chat-adapter-line#34` the model wrote `File: src/message.ts` with no line, the parser folded the finding into the body, and the review posted as one long timeline comment. `agent/lib/github/anchors.ts` now reads `GET /pulls/{number}/files` after the reply and settles every finding: no line goes to the file's first added line, a line outside the diff to the nearest changed line, and a file the diff does not touch into the body. A wrong line that is inside the diff stays where the model put it, and a suggestion block replaces that exact line, so that part is still the model's.

**The model can write a tool result instead of calling the tool (2026-09-16).** The review of baymi#31 ran `load_skill` and one `glob`, then answered with `Tool (read_file): [{"content": "1: /**…"}]` and stopped: 12,080 characters of two files from the pull request, line-numbered, in the shape thaipass renders a settled tool result into the transcript (`packages/core/src/translate.ts`, `Tool (${name})`). No `read_file` reached the runtime; the telemetry lists two tools. The model was DeepSeek-V3.2. The grounding guard passed on the two settled actions, `parseReview` answered null, and the fallback posted the fabrication as a timeline comment. Two rules now hold: a skill load does not ground a turn, and the step escape asks for two steps, because the three other reviews that afternoon (chat-adapter-line#33, #34 and #35) loaded the skill and answered from the truncated diff without opening the checkout; and an unattended reply the parser rejects goes to Slack as `review_not_a_review`, never to the pull request. A fabricated read followed by a well-formed review passes both. Nothing on this side can tell it from a real one.

**Authored channels report `channel:<name>`, framework ones report a bare name.** `agent/channels/github.ts` is `channel:github`, while `http` arrives bare. Comparing `ctx.channel.kind === "github"` never matches, silently, and a fragment gated that way loads everywhere. `channelName` in `agent/lib/instructions.ts` normalizes it, and every comparison goes through there.

**An approval card outlives the session that raised it, and then Approve does nothing.** Slack renders the card, Connect forwards the click, and the route answers 200, but the pause it answers lives in the session, so once the session is gone the click resolves nothing and the card stays on screen looking answerable. Observed 2026-09-01 (six clicks, each logging `Cannot deliver inputResponses — the target session was not found via continuation token`). An unattended turn fails from the other end: nobody is watching while its session is alive. That is why every write on an unattended turn is refused rather than carded (`agent/lib/github/approval.ts`), and why the review fragment says not to ask questions.

**A failed queue delivery re-runs the turn, and side effects go with it.** Delivery is at-least-once: a `TypeError: fetch failed` mid-turn produced `[workflow-sdk] Re-executing inline steps owned by this queue message` and a second, freshly composed copy of the same message. Any write the agent makes can happen twice when the transport drops mid-turn. A duplicated review comment or check-in is the cost; nothing guards against it today, and a guard would have to be idempotency at the step level.

**A failed sandbox checkout is swallowed, and the turn runs against an empty tree.** When git answers `detected dubious ownership`, eve logs `GitHub checkout failed — swallowed` and continues, so `read_file`, `glob` and `grep` find no files and the agent reports a clean review of nothing. `agent/sandbox.ts` marks `/workspace` safe in bootstrap. A review that says "checked and clean" over a change it plainly should have flagged is the symptom to look for.

**A handler in `events` replaces eve's built-in, and `turn.started` is the checkout.** The type says it outright: "A handler supplied here replaces the built-in for that key rather than running alongside it", and the built-in `turn.started` is what adds the eyes reaction and checks the repository out. Anything that wants to run at the start of a review goes somewhere else; the check run opens in `onPullRequest`, which takes a promise and carries both `ctx.github.request` and the head sha. `channel.state.headSha` is no use there — the checkout-derived fields start null and it is that same `turn.started` handler that fills them in.

**A push reviews in the same session, and its channel state is the first dispatch's (2026-10-21).** `onPullRequest` runs on every `synchronize`, but the turn joins the pull request's session, and eve 0.62 keeps that session's state: `channel.state.headSha` stays on the commit the session opened with, and the built-in checkout writes back the sha it was handed. Every follow-up then settled the first commit's check run again, and the run opened on the new head stayed `in_progress` for good. On 2026-10-21, all 57 agent runs in the last three days were in that state. Summaries also said `Reviewed at` the first commit. `refreshHeadSha` in `agent/channels/github.ts` reads the head from GitHub before anything is settled. The sandbox checkout of a follow-up still starts from the sha the previous turn left, because nothing runs before the built-in `turn.started`. The diff in context comes from the dispatch, so it is current.

**Snapshot storage grows by one snapshot per review, and running out fails the build (2026-09-20).** `eve build` prewarms the sandbox template, so a plan with no snapshot storage left answers 402 and the deployment dies there, before anything the change touched runs. `keepLastSnapshots: { count: 1 }` bounds what one sandbox keeps, and every session creates its own sandbox, so the project's total is bounded by `snapshotExpiration` and nothing else: it held 94 snapshots and 25.95 GB, 84 of them session snapshots of about 150 MB under a seven-day expiry, against 19 reviews on 2026-09-19 alone. The other ten were template roots left by earlier builds, five from before the base image shrank, 723-842 MB each and unread since 2026-09-04. Session expiry is one day now. Reading them back: `vercel sandbox snapshots list --project baymi --scope pungrumpy` caps `--limit` at 50 and writes its table to stderr when stdout is a pipe, and `GET https://vercel.com/api/v2/sandboxes/snapshots?teamId=<team>&project=<project>` is the same data as JSON with `parentId`, which is what tells a template root from a session snapshot. Deleting the children settles the root with them: six of the nine dead roots answered `is in status "deleted" and cannot be deleted` when named afterwards.

**On Hobby, a sandbox that outlives its turn uses quota the reviews need (2026-10-01).** Hobby includes 15 GB of snapshot storage for the life of the account, plus 420 GB-hours of provisioned memory and 5 active CPU hours a month. When any of them runs out, Vercel pauses sandbox creation for 30 days, and every review in that time fails. eve's Vercel backend stops an idle VM after 30 minutes, so a 2-vCPU sandbox (4 GB) used about 2 GB-hours after each reply. At that rate, idle time alone uses the monthly memory quota in about 210 reviews.

The GitHub channel now deletes the sandbox and its snapshots after a turn posts its reply (`agent/lib/sandbox.ts`), and the sandbox runs on one vCPU. The delete is safe because eve's GitHub channel checks the repository out in `turn.started` on every turn. `checkoutRepositoryForTurn` skips the checkout only when HEAD is already the wanted sha, so a later push or mention gets a new sandbox with the head checked out.

The delete never runs on an empty message. eve can reissue a model call that returned an empty response, so an empty message may not end the turn. A delete at that point would leave the rest of the turn searching an empty tree. `turn.failed` and `session.failed` do not delete either, because `ctx.getSandbox()` creates a new sandbox after a delete. A second delete in the same turn would create a sandbox only to delete it, so `snapshotExpiration` removes a failed turn's sandbox instead.

**The diff in context is a summary, capped at 20 KB.** `buildGitHubPullRequestContext` lists at most 50 files and spends a shared `MAX_PATCH_BYTES` budget of 20,000 bytes across their patches, appending `patches_truncated: true` once the budget runs out; lockfiles, minified output, maps and snapshots are dropped before that. A 45-file pull request arrives as a few whole patches and a list of filenames. On those reviews the checkout is the only way to read the code, which is why a turn that never opened it cannot report on one (`agent/lib/github/grounding.ts`).

**`pullRequest.raw` is the pull request, not the webhook envelope (2026-09-19).** `dispatch.js` calls the handler with `event.pullRequest`, whose `raw` eve built from `payload.pull_request`, so `raw.draft` is the field and `raw.pull_request.draft` is nothing. `shouldReviewPullRequest` read the second one from the day it was written and reviewed every draft; the test passed because its fixture was the envelope. A fixture for a handler argument has to be the shape the handler is handed, not the shape the webhook arrived in.

**Only the GitHub channel checks out the repository.** It happens before the first model call, at the triggering ref. On Slack and on the HTTP route `/workspace` is empty, which is why the Slack fragment points a full review back at the pull request thread.

**`defaultTools: false` removes every optional default, including `load_skill` and `ask_question`.** eve 0.52.2 added the option; with it set, `eve info` listed only `glob`, `grep`, and the authored tool until `read_file`, `load_skill`, and `ask_question` were added back under `agent/tools/` as one-line re-exports. `connection_search` survives on its own when connections exist. The removal is static either way: there is no per-session way to remove a built-in, so `bash` is off everywhere rather than off on unattended turns. A maintainer-only shell would be a dynamic tool that wraps `eve/tools/bash`, resolved by `isUnattended`; nothing needs it yet.

**A dynamic subagent compiles eve's default tools in, whatever its `defaultTools` says (2026-10-02).** `agent/subagents/remediation/agent.ts` returns `defineAgent({ defaultTools: false, ... })` from a `defineDynamic` resolver. `.eve/compile/compiled-agent-manifest.json` still listed `todo`, `web_fetch`, `load_skill`, `ask_question` and `web_search` under `subagents[0].agent.tools`, because the compiler decides the tool set before any resolver runs. Whether the runtime then honors `defaultTools: false` is not documented, and `web_fetch` runs in the app runtime, outside the sandbox's egress allow-list, so it was not left to chance. Each default the subagent must not have is a file under its own `tools/` that exports `disableTool()`, and the manifest now lists only `task_cancel` and the subagent's own eight. Read that manifest after adding a dynamic subagent. `eve info` reports only the root's tool count.

**Dynamic tools: executes stay inline.** eve's bundler registers a dynamic tool's `execute` as a durable step only when the function sits inline in the resolver body. A tool built by a factory, or returned from an implicit arrow, type-checks, works on a fresh session, and fails on a resumed one with `references step function "..." which is not registered`. `agent/tools/notify_maintainer.ts` is written the way it is for that reason, and so are the inline approval policies in `agent/extensions/github/extension.ts`.

**A memory scope that resolves to `null` disables the slot for that turn.** Recall does not run and the provider's tools are not offered. That is the whole mechanism keeping an unattended review out of the maintainer's memory (`agent/memory/file.ts`). Read-only is the exception, and it takes a wrapper on the provider, below.

**Schedules do not fire in dev, and there are none here.** If one is added, `curl -X POST http://localhost:2000/eve/v1/dev/schedules/<name>` triggers it manually and answers `{ "scheduleId", "sessionIds": [...] }`. A handler-form schedule that never calls `to(...).send(...)` starts no session, so `sessionIds` is empty.

**A schedule's turn runs as `eve:app`, a `runtime` principal (measured on `eve dev` 0.62.0, 2026-10-23).** A throwaway markdown schedule fired through the route above started a session whose memory-scope resolver received this, with `current` and `initiator` the same object and the channel `{ "kind": "schedule", "metadata": {} }`:

```json
{
  "attributes": {},
  "authenticator": "app",
  "principalId": "eve:app",
  "principalType": "runtime"
}
```

A handler-form schedule's `appAuth` logged the identical object. The handler form was not run through `to(...).send(...)`: every target is a channel that would post to a real Slack or GitHub conversation, and eve's docs say the session runs as the `auth` passed in, which is `appAuth`. The same probe on the HTTP route under `localDev()` gave `{ "authenticator": "local-dev", "principalId": "local-dev", "principalType": "local-dev" }` on channel `http`. `agent/lib/trust.ts` classifies `eve:app` as `app` (`APP_PRINCIPAL`); the test fixture is the object above. A Vercel OIDC token for this project is also `runtime`, under a `<issuer>:<subject>` id, so the class keys on the id and the type together. eve's `byPrincipal` scope returns `null` for `runtime`, which is why the memory slot is not scoped by it.

**File memory can recall without offering its save and remove tools (2026-10-23).** A slot's scope picks the document and `provider.tools(ctx)` picks the tools, and `ctx.session.auth` reaches both. `withMemoryAccess` in `agent/lib/memory.ts` wraps `fileMemory()` so `tools()` returns `null` unless the caller may write, which leaves the app turn with recall and no tool that changes the document. File memory has no capture step, so nothing else writes. Measured on `eve dev` with Sonnet 5.5: a maintainer turn over HTTP saved a codeword and, asked which of its tools have `memory` in the name, answered `file__remove_memory` and `file__save_memory`; a schedule turn asked the same listed none and gave back the codeword from recalled memory. eve rebuilds a provider tool on replay by calling `provider.tools()` with the stored context, so the gate holds when a step replays. The alternatives do not fit: `agent/tools/file.ts` exporting `disableTool()` removes the tools on every turn, and a scope resolver has one answer per turn, not one per operation. Recalled memory reaches the model as a user-role message, and the model treated a recalled block that read like instructions as data, which is the posture `agent/instructions.md` asks for.

**The CLI runs on Node, not on Bun, and refuses anything below 24.** Invoking it through `bun run` does not change that, so CI needs `actions/setup-node` alongside `setup-bun`.

**eve 0.62 needs `ai` >= 7.0.105, and an `overrides` floor can hold it below that (2026-09-19).** `ai` is a peer dependency, so nothing fails at install: discovery dies later with `The requested module 'ai' does not provide an export named 'experimental_evaluate'`, blamed on whichever authored module loaded first, which here was the GitHub extension's tool file rather than anything at fault. `package.json` carried `overrides.ai: "^7.0.38"`, and `bun add ai@latest` kept resolving 7.0.97 under it while npm had 7.0.107. Raising the override to `^7.0.105` and deleting `bun.lock` fixed it. Read the peer range off `node_modules/eve/package.json`, not the changelog.

**eve 0.63.0 does not mount `@github-tools/eve-extension` 0.7.2 (2026-09-19).** `eve info` fails with `Selected module binding "extensions/github.ts" has no compile or runtime usage`, from the compiler's module-lifecycle check: the mount is discovered but neither compile-loaded nor reachable as a runtime entry. The extension was published 2026-09-19 10:44 and eve 0.63.0 at 16:38 the same day, so it predates the release. 0.62.0 mounts it and validates with no diagnostics, and 0.62.0 is where the autoevals removal landed, so it is the version to sit on until the extension ships against 0.63.

**eve does not load `.env` during discovery.** `eve info` and `eve build` read the process environment only; the README shows the `env $(...)` form. `vercel env pull` writes `GITHUB_WEBHOOK_SECRET` to `.env.local`, so a discovery run needs both files.

## GitHub

**The App's slug is what the code needs, not its display name.** The slug is both the handle people mention and the stem of the `[bot]` login the self-comment guard compares against. `baymi` was taken, hence `baymiai`, and the line in `agent/instructions.md` telling the model both names are it.

**Webhooks go straight from the App, not through Connect's forwarder.** Forwarding is metered per delivery and the events are identical either way. `connectGitHubCredentials` returns a `webhookVerifier` for the forwarder's signature, and eve skips the `webhookSecret` path whenever a verifier is present, so `agent/lib/github/credentials.ts` drops the verifier and supplies the App's own secret.

**`defaultGitHubAuth` stamps the repository and pull request number on `attributes`.** `repository` is `owner/repo` and `pull_request_number` is a string, empty on an issue session. `pullRequestFromAuth` reads them, which is how the check-in tool knows which pull request it is on without taking a target from the model.

**A tool set is priced per turn.** Every tool in the prompt on every turn costs tokens, and the `maintainer` preset alone is 79 of them; this agent mounts 19 GitHub tools, 11 of them on a review turn, and 8 of its own on a review. The reliability half of this note used to say that 42% of turns made zero tool calls at 18 or more tools against 5% at one to three, measured 2026-09-03. The gateway's own request log does not support that: over 14 days, zero-call turns run 24.2% at 1-5 tools and 15.4% at 18-29. The 2026-09-03 figure was collected while requests ran concurrently, which is the confound described below. Keep the list short for the tokens. A short list does not make the turn more reliable.

**GitHub's dependency graph does not read `bun.lock`, and on most of these repositories it is off (2026-10-02).** `GET /dependency-graph/sbom` answered 404 on nine of the ten installed repositories, and `/dependency-graph/compare` answered 403 on `baymi`. On `logixlysia`, the one where it answered, the SBOM listed only `package.json` entries with their ranges, such as `pkg:npm/vitest@%5E5.0.1`, and none of the 1,376 packages its `bun.lock` installs. Both readers now go to the root `bun.lock` or `package-lock.json` first (`agent/lib/remediation/lockfile.ts`). Remediation reads it at the base commit. `list_dependency_changes` compares it at the pull request's base and head, and asks the global advisory database about what was added, a hundred packages per call (`readAdvisoriesForPackages`). GitHub's own comparison is the fallback for projects without one. Run against `pigo#43`, the lockfile comparison found 84 added packages, among them `undici@7.29.0`, which has published advisories. Read with that, the same day, eight of the ten repositories had packages with published advisories.

**One advisory can carry a range per release line, each with its own patch (2026-10-02).** `GHSA-pmjh-fq2x-6v4x` lists `undici` twice: `>= 7.11.0, < 7.29.1` patched in 7.29.1, and `>= 8.0.0, < 8.10.2` patched in 8.10.2. The first version of `readAdvisories` took the first entry whose package name matched, and resolved `undici` 8.9.0 on `baymi` to a "fix" of 7.29.1, a downgrade. It now takes the entry whose range holds the version in use (`isInRange`), and `upgradeTarget` refuses any target that is not newer than every version in use. Run the resolver against a real repository after changing it. The unit tests passed with the bug in place, because every fixture had one range.

**`getPullRequestContext` is the one-call read.** It returns the pull request, its metadata and recent comments together; `listPullRequestFiles` adds the patches. On a GitHub turn neither is needed for the pull request under review, since the diff is already in context and the code is in the checkout.

**The eight CI tools cost about 2,000 tokens a turn, and the extension cannot leave them out of one (2026-10-23).** On `eve dev`, over the HTTP route, the same one-line question took 7,960 input tokens with all 19 GitHub tools offered and 5,899 with the eight CI ones withheld, a difference of 2,061 on `moonshotai/kimi-k2.7-code`. The Claude tokenizer reads the same tool block as 4,595 tokens for the original 11 and 7,679 for all 19 (`POST /v1/messages/count_tokens`, `claude-sonnet-5-5`), 3,084 more. The extension resolves its `include` at `step.started` with nothing from the turn to branch on, and an approval policy runs when the model calls a tool, which is after the tool has been paid for in the prompt. What eve does allow is replacing a mounted contribution: `agent/extensions/github/tools/github.ts` takes the extension's own resolver (`github` from `@github-tools/eve-extension/tools`), calls it, and drops the CI tools from the result when `toolsForTurn` says the turn is the reviewer's. The tools, their policies and their durable callbacks are the extension's, untouched. Verified on a scratch copy with the cut keyed on the `local-dev` principal: the tool list in the reply went from 21 names to 13 and the input from 7,960 to 5,899 tokens. Not verified with a real `github:baymiai` turn, which needs a signed webhook and opens a check run on a real pull request; `toolsForTurn` is tested with the reviewer fixture. The cut asks for the reviewer by name rather than `isUnattended`, because unit L2 widens `isUnattended` to the app's own scheduled turns, and those are the turns that read CI.

**`searchIssues` reaches past the installation, and nothing after it does (2026-10-23).** `author:PunGrumpy is:pr is:open draft:false updated:>=2026-09-23` returned 21 pull requests, the same 21 non-draft ones `gh search prs` finds with PunGrumpy's own token. One of them is `veggiemonk/awesome-docker#1573`, a public repository the App is not installed on (`list_installed_repositories` names 13, all PunGrumpy's). `listWorkflowRuns` on that repository answered too, since an installation token reads public data. So the lead sees upstream contributions in a search unless the query says `user:PunGrumpy`, and everything it could do there is a read: the check and workflow webhooks only arrive from installed repositories, and a write would be refused. Whether the search returns a private repository the App is not installed on was not tested; no such repository has an open pull request by PunGrumpy, since the two result sets match.

**GitHub lists only open pull requests on a workflow run (2026-10-23).** Run `39823444170` of open `baymi#52` carries `pull_requests: [{number: 52, ...}]`. Three failed runs on branches whose pull requests have since merged (`logixlysia#503`, `logixlysia#510`, `vecstore-sdk#53`) carry `[]`, and so does a push to `main` (`pigo`, `baymi`). A fork's pull request carries none either. The rerun guard (`agent/lib/github/rerun.ts`) has nothing to compare a head against for any of them and refuses: "attached to no open pull request".

**The rerun guard trusts GitHub's attempt count, and two things about it are unmeasured (2026-10-23).** `run_attempt` is read on every call, so a turn delivered twice finds attempt 2 the second time and is refused. Nothing here has seen a real rerun: no open pull request had a failed run, and a rerun on a real repository was out of bounds, so the claim that GitHub reports attempt 2 as soon as it accepts a rerun rests on its documentation. Two calls racing before that happens are not covered, and neither is a step replayed after GitHub accepted the rerun but before eve recorded it, if eve does not ask the policy again on replay. The installation token reads runs, jobs and job logs (`x-accepted-github-permissions: actions=read`, 200); whether the App has `actions: write` is unverified, and the rerun answers 403 if it does not. The HTTP route's principal is `local-dev` with type `local-dev`, not `user`, so `eve dev` cannot reach an allowed rerun; the guard was run with a `user` fixture and the real installation token against two successful runs, and refused both with "ended success".

## Slack

**The Slack principal is `slack:<team>:<member>`.** `defaultSlackAuth` mints it from the event's `team_id` and the actor's id, and bots get `slack:<team>:bot:<id>`. `isSlackHuman` trusts every human of the workspace, pinned to `SLACK_TEAM_ID` when set; the workspace is private, so membership is the allowlist. Replies in a thread the agent owns need the connector's trigger to subscribe `message.channels` with `channels:history`; without them only mentions and DMs arrive.

**Vercel's Slack deployment message, read off a screenshot (2026-09-11).** A status dot emoji and a bold headline ("🟢 Feat/webhooks (#15) deployed successfully"), then a colored left bar holding "By AshikNesin on `main`" and "858f54e | nesins-finance-app | via GitHub | Today at 10:35 AM", then a green primary "Visit" button beside a plain "Inspect". The bar is a legacy `attachments[].color`, which Slack still renders around `blocks`. `checkInMessage` in `agent/lib/slack/notify.ts` reproduces that shape: dot and headline as a top-level section, details and the two buttons inside one colored attachment, and the time as `<!date^…>` so Slack renders it in the reader's zone.

**`chat.postMessage` to a member ID needs the DM opened first.** `conversations.open` with `users=<id>` returns the `D…` conversation; posting to the `U…` id directly fails on some workspaces. `postSlackMessage` does the two calls when the target is a member, one when it is a channel.

## Configuration

**`imports` wildcards in `package.json` are literal substitutions.** `#*` mapped to `./agent/*` does no extension resolution, which is why the map includes the `.js` suffix (`"#*": "./agent/*.js"`) so call sites read as `#lib/env`.

**`emptyStringAsUndefined: true` makes `VAR=""` unset, not empty.** A required variable with an empty value fails discovery as "missing" rather than as a validation error, and `.env.example` placeholders written as `""` are only runnable for the optional block.

## Model access

**The model is a gateway id, and the deployment's OIDC token is the credential (2026-10-19).** eve routes a `provider/model` string through Vercel AI Gateway, so `agent/lib/model.ts` is the whole configuration. On Vercel the deployment's OIDC token authenticates it. Locally, `vercel env pull .env.local` writes `VERCEL_OIDC_TOKEN`, which `eve dev`, `eve eval` and `scripts/review-bench.ts` read. The token expires, so pull again when the gateway answers 401. Until this date the agent ran on thaipass, an Anthropic-protocol proxy in front of AI Pass, and most of what this file used to say about models was about that proxy: emulated tool calls, a daily credit allowance, an edge that refused prompts on their content, silent model substitution. ## Tooling

**`ultracite fix` rewrites test code, not only its formatting.** Observed: trailing `undefined` arguments dropped (which changes the call and breaks the types when the parameter is not optional), `toBe(false)` rewritten to `toBeFalsy()`, and `describe("name")` rewritten to `describe(name)` when an identifier of that name is in scope, which only type-checks if the identifier is a function. Make optional parameters optional, label `describe` blocks with phrases rather than identifiers, and read a file back after formatting it.

## Deployment

**Vercel Deployment Protection answers before the app does.** Every route on a protected preview returns 401 or a redirect to Vercel SSO, including the webhook paths, so GitHub and Slack cannot reach a protected preview at all: point the webhooks at production.

**`ai.model` is empty unless the hook is told the model.** evlog reads the model from the id eve reports at `session.started`, and with a static gateway id that still arrives empty: a turn on 2026-10-19 without the option logged `ai: 1 call` and no model. `agent/hooks/evlog.ts` passes `model: MODEL`. `ai.estimatedCost` stays empty because evlog computes it only from a `cost` map. The dashboards count tokens.

**PostHog has two hosts and they are not interchangeable.** `POSTHOG_HOST` is the _capture_ endpoint (`us.i.posthog.com`, note the `i`); the query endpoint is `us.posthog.com`. Posting events at the query host does not fail loudly enough to be obvious.
