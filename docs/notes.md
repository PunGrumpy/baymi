# Notes

Things that cost time to find out. Each one is why some line of this agent, or of its tooling, looks the way it does, kept here so the code does not have to hold the paragraph.

## eve

**The channel posts the turn's own message, so a comment tool posts a second one.** eve's GitHub channel installs a `message.completed` handler that posts any completed message into the thread the session is anchored to. A turn that answers by calling `github__addIssueComment` or `github__addPullRequestComment` is posted twice, once as the tool's comment and once as the reply narrating that it posted it. Every GitHub instruction here says the reply is the comment; the comment tools are for writing on some _other_ thread.

**The channel posts the review, not a tool.** `github__createPullRequestReview` exists in github-tools and takes `event` plus inline `comments[]`, but mounting it would mean either trusting the model with `APPROVE`/`REQUEST_CHANGES` (gateable on the payload) or posting twice, since the built-in `message.completed` handler posts the reply anyway. `agent/channels/github.ts` overrides that handler instead: the reply is parsed (`agent/lib/github/review.ts`) and submitted as one review with a fixed `COMMENT` event, and a reply that is not a review is posted as a comment the way the default did. GitHub answers 422 for an inline comment on a line outside the diff, and one bad line fails the whole review, so any failure falls back to a plain comment and logs the error rather than losing the findings. `splitComment` replaces eve's `splitGitHubCommentBody`, which is not exported.

**Vercel Agent's review format, read off two public pull requests (2026-09-11).** No summary comment. One review with `COMMENTED` state and an empty body, one inline comment per finding, one sentence each, a "Fix on Vercel" image link to a sandbox-validated patch, and hidden `<!-- VADE-… -->` markers for category, recommendation, head and base SHA, review id and task id. When a human disputes a finding it replies in the thread and marks `<!-- VADE-OUTCOME: ISSUE_RESOLVED -->`. Baymi copies the shape (inline, one line visible, markers for a second look) and not the button, because a button that looks validated over a patch nobody ran would be a lie; GitHub's native `suggestion` block is the honest equivalent. The body is the count line and nothing else. `anchorReview` cuts it to that line whatever the model wrote, because the skill alone did not hold: the review on chat-adapter-line#34 opened with two paragraphs describing the feature to its author. The `ai-sdk-factory` rubric on `vercel/ai#20792` (title, `Outcome:`, one `Risk:` section per concern) was tried for the body on 2026-09-16 and dropped the same day. It is a summary comment, which this shape exists to avoid.

**The model cannot count diff lines, so the channel anchors findings for it (2026-09-16).** The diff in context is a unified patch, so a `File: path:line` needs the new-side number computed from a hunk header by hand. On `chat-adapter-line#34` the model wrote `File: src/message.ts` with no line, the parser folded the finding into the body, and the review posted as one long timeline comment. `agent/lib/github/anchors.ts` now reads `GET /pulls/{number}/files` after the reply and settles every finding: no line goes to the file's first added line, a line outside the diff to the nearest changed line, and a file the diff does not touch into the body. A wrong line that is inside the diff stays where the model put it, and a suggestion block replaces that exact line, so that part is still the model's.

**The model can write a tool result instead of calling the tool (2026-09-16).** The review of baymi#31 ran `load_skill` and one `glob`, then answered with `Tool (read_file): [{"content": "1: /**…"}]` and stopped: 12,080 characters of two files from the pull request, line-numbered, in the shape thaipass renders a settled tool result into the transcript (`packages/core/src/translate.ts`, `Tool (${name})`). No `read_file` reached the runtime; the telemetry lists two tools. The model was DeepSeek-V3.2. The grounding guard passed on the two settled actions, `parseReview` answered null, and the fallback posted the fabrication as a timeline comment. Two rules now hold: a skill load does not ground a turn, and the step escape asks for two steps, because the three other reviews that afternoon (chat-adapter-line#33, #34 and #35) loaded the skill and answered from the truncated diff without opening the checkout; and an unattended reply the parser rejects goes to Slack as `review_not_a_review`, never to the pull request. A fabricated read followed by a well-formed review passes both. Nothing on this side can tell it from a real one.

**Authored channels report `channel:<name>`, framework ones report a bare name.** `agent/channels/github.ts` is `channel:github`, while `http` arrives bare. Comparing `ctx.channel.kind === "github"` never matches, silently, and a fragment gated that way loads everywhere. `channelName` in `agent/lib/instructions.ts` normalizes it, and every comparison goes through there.

**An approval card outlives the session that raised it, and then Approve does nothing.** Slack renders the card, Connect forwards the click, and the route answers 200, but the pause it answers lives in the session, so once the session is gone the click resolves nothing and the card stays on screen looking answerable. Observed 2026-09-01 (six clicks, each logging `Cannot deliver inputResponses — the target session was not found via continuation token`). An unattended turn fails from the other end: nobody is watching while its session is alive. That is why every write on an unattended turn is refused rather than carded (`agent/lib/github/approval.ts`), and why the review fragment says not to ask questions.

**A failed queue delivery re-runs the turn, and side effects go with it.** Delivery is at-least-once: a `TypeError: fetch failed` mid-turn produced `[workflow-sdk] Re-executing inline steps owned by this queue message` and a second, freshly composed copy of the same message. Any write the agent makes can happen twice when the transport drops mid-turn. A duplicated review comment or check-in is the cost; nothing guards against it today, and a guard would have to be idempotency at the step level.

**A failed sandbox checkout is swallowed, and the turn runs against an empty tree.** When git answers `detected dubious ownership`, eve logs `GitHub checkout failed — swallowed` and continues, so `read_file`, `glob` and `grep` find no files and the agent reports a clean review of nothing. `agent/sandbox.ts` marks `/workspace` safe in bootstrap. A review that says "checked and clean" over a change it plainly should have flagged is the symptom to look for.

**A handler in `events` replaces eve's built-in, and `turn.started` is the checkout.** The type says it outright: "A handler supplied here replaces the built-in for that key rather than running alongside it", and the built-in `turn.started` is what adds the eyes reaction and checks the repository out. Anything that wants to run at the start of a review goes somewhere else; the check run opens in `onPullRequest`, which takes a promise and carries both `ctx.github.request` and the head sha. `channel.state.headSha` is no use there — the checkout-derived fields start null and it is that same `turn.started` handler that fills them in.

**A push reviews in the same session, and its channel state is the first dispatch's (2026-10-21).** `onPullRequest` runs on every `synchronize`, but the turn joins the pull request's session, and eve 0.62 keeps that session's state: `channel.state.headSha` stays on the commit the session opened with, and the built-in checkout writes back the sha it was handed. Every follow-up then settled the first commit's check run again, and the run opened on the new head stayed `in_progress` for good. On 2026-10-21, all 57 agent runs in the last three days were in that state. Summaries also said `Reviewed at` the first commit. `refreshHeadSha` in `agent/channels/github.ts` reads the head from GitHub before anything is settled. The sandbox checkout of a follow-up still starts from the sha the previous turn left, because nothing runs before the built-in `turn.started`. The diff in context comes from the dispatch, so it is current.

**Snapshot storage grows by one snapshot per review, and running out fails the build (2026-09-20).** `eve build` prewarms the sandbox template, so a plan with no snapshot storage left answers 402 and the deployment dies there, before anything the change touched runs. `keepLastSnapshots: { count: 1 }` bounds what one sandbox keeps, and every session creates its own sandbox, so the project's total is bounded by `snapshotExpiration` and nothing else: it held 94 snapshots and 25.95 GB, 84 of them session snapshots of about 150 MB under a seven-day expiry, against 19 reviews on 2026-09-19 alone. The other ten were template roots left by earlier builds, five from before the base image shrank, 723-842 MB each and unread since 2026-09-04. Session expiry is one day now. Reading them back: `vercel sandbox snapshots list --project baymi --scope pungrumpy` caps `--limit` at 50 and writes its table to stderr when stdout is a pipe, and `GET https://vercel.com/api/v2/sandboxes/snapshots?teamId=<team>&project=<project>` is the same data as JSON with `parentId`, which is what tells a template root from a session snapshot. Deleting the children settles the root with them: six of the nine dead roots answered `is in status "deleted" and cannot be deleted` when named afterwards.

**On Hobby, a sandbox that outlives its turn uses quota the reviews need (2026-10-01).** Hobby includes 15 GB of snapshot storage for the life of the account, plus 420 GB-hours of provisioned memory and 5 active CPU hours a month. When any of them runs out, Vercel pauses sandbox creation for 30 days, and every review in that time fails. eve's Vercel backend stops an idle VM after 30 minutes, so a 2-vCPU sandbox (4 GB) used about 2 GB-hours after each reply. At that rate, idle time alone uses the monthly memory quota in about 210 reviews.

The GitHub channel now deletes the sandbox and its snapshots after a turn posts its reply (`agent/lib/sandbox.ts`), and the sandbox runs on one vCPU. The delete is safe because eve's GitHub channel checks the repository out in `turn.started` on every turn. `checkoutRepositoryForTurn` skips the checkout only when HEAD is already the wanted sha, so a later push or mention gets a new sandbox with the head checked out.

The delete never runs on an empty message. eve can reissue a model call that returned an empty response, so an empty message may not end the turn. A delete at that point would leave the rest of the turn searching an empty tree. `turn.failed` and `session.failed` do not delete either, because `ctx.getSandbox()` creates a new sandbox after a delete. A second delete in the same turn would create a sandbox only to delete it, so `snapshotExpiration` removes a failed turn's sandbox instead.

**The diff in context is a summary, capped at 20 KB.** `buildGitHubPullRequestContext` lists at most 50 files and spends a shared `MAX_PATCH_BYTES` budget of 20,000 bytes across their patches, appending `patches_truncated: true` once the budget runs out; lockfiles, minified output, maps and snapshots are dropped before that. A 45-file pull request arrives as a few whole patches and a list of filenames. On those reviews the checkout is the only way to read the code, which is why a turn that never opened it cannot report on one (`agent/lib/github/grounding.ts`).

**`pullRequest.raw` is the pull request, not the webhook envelope (2026-09-19).** `dispatch.js` calls the handler with `event.pullRequest`, whose `raw` eve built from `payload.pull_request`, so `raw.draft` is the field and `raw.pull_request.draft` is nothing. `shouldReviewPullRequest` read the second one from the day it was written and reviewed every draft; the test passed because its fixture was the envelope. A fixture for a handler argument has to be the shape the handler is handed, not the shape the webhook arrived in.

**Only the GitHub channel checks out the repository.** It happens before the first model call, at the triggering ref. On Slack and on the HTTP route `/workspace` is empty, which is why the Slack fragment points a full review back at the pull request thread.

**`defaultTools: false` removes every optional default, including `load_skill` and `ask_question`.** eve 0.52.2 added the option; with it set, `eve info` listed only `glob`, `grep`, and the authored tool until `read_file`, `load_skill`, and `ask_question` were added back under `agent/tools/` as one-line re-exports. `connection_search` survives on its own when connections exist. The removal is static either way: there is no per-session way to remove a built-in, so `bash` is off everywhere rather than off on unattended turns. A maintainer-only shell would be a dynamic tool that wraps `eve/tools/bash`, resolved by `isUnattended`; nothing needs it yet.

**A dynamic subagent compiles eve's default tools in, whatever its `defaultTools` says (2026-10-02), and eve 0.62.0 then refuses that field at runtime (2026-10-22).** The remediation subagent returned `defineAgent({ defaultTools: false, ... })` from a `defineDynamic` resolver. `.eve/compile/compiled-agent-manifest.json` still listed `todo`, `web_fetch`, `load_skill`, `ask_question` and `web_search` under its tools, because the compiler decides the tool set before any resolver runs, so each default was disabled by name. At runtime eve refused the field (`The "defaultTools" field cannot be selected at runtime`), logged `omitting subagent`, and the root never had the subagent to call; a resolver also cannot return a provider object, only a gateway id string. That subagent is gone. The chase that replaced it is static (`agent/subagents/chase/agent.ts`), where `defaultTools: false` and a direct `anthropic(...)` model are both accepted, and the manifest lists only its own nine tools. Read that manifest after adding a subagent; `eve info` reports only the root's tool count.

**Dynamic tools: executes stay inline.** eve's bundler registers a dynamic tool's `execute` as a durable step only when the function sits inline in the resolver body. A tool built by a factory, or returned from an implicit arrow, type-checks, works on a fresh session, and fails on a resumed one with `references step function "..." which is not registered`. `agent/tools/notify_maintainer.ts` is written the way it is for that reason, and so are the inline approval policies in `agent/extensions/github/extension.ts`.

**A memory scope that resolves to `null` disables the slot for that turn.** Recall does not run and the provider's tools are not offered. That is the whole mechanism keeping an unattended review out of the maintainer's memory (`agent/memory/file.ts`). Read-only is the exception, and it takes a wrapper on the provider, below.

**Schedules do not fire in dev, and there are none here.** If one is added, `curl -X POST http://localhost:2000/eve/v1/dev/schedules/<name>` triggers it manually and answers `{ "scheduleId", "sessionIds": [...] }`. A handler-form schedule that never calls `to(...).send(...)` starts no session, so `sessionIds` is empty.

**A schedule's turn runs as `eve:app`, a `runtime` principal (measured on `eve dev` 0.62.0, 2026-10-23).** A throwaway markdown schedule fired through the route above started a session whose memory-scope resolver received this, with `current` and `initiator` the same object and the channel `{ "kind": "schedule", "metadata": {} }`:

```json
{
  "attributes": {},
  "authenticator": "app",
  "principalId": "eve:app",
  "principalType": "runtime"
}
```

A handler-form schedule's `appAuth` logged the identical object. The handler form was not run through `to(...).send(...)`: every target is a channel that would post to a real Slack or GitHub conversation, and eve's docs say the session runs as the `auth` passed in, which is `appAuth`. The same probe on the HTTP route under `localDev()` gave `{ "authenticator": "local-dev", "principalId": "local-dev", "principalType": "local-dev" }` on channel `http`. `agent/lib/trust.ts` classifies `eve:app` as `app` (`APP_PRINCIPAL`); the test fixture is the object above. A Vercel OIDC token for this project is also `runtime`, under a `<issuer>:<subject>` id, so the class keys on the id and the type together. eve's `byPrincipal` scope returns `null` for `runtime`, which is why the memory slot is not scoped by it.

**File memory can recall without offering its save and remove tools (2026-10-23).** A slot's scope picks the document and `provider.tools(ctx)` picks the tools, and `ctx.session.auth` reaches both. `withMemoryAccess` in `agent/lib/memory.ts` wraps `fileMemory()` so `tools()` returns `null` unless the caller may write, which leaves the app turn with recall and no tool that changes the document. File memory has no capture step, so nothing else writes. Measured on `eve dev` with Sonnet 5.5: a maintainer turn over HTTP saved a codeword and, asked which of its tools have `memory` in the name, answered `file__remove_memory` and `file__save_memory`; a schedule turn asked the same listed none and gave back the codeword from recalled memory. eve rebuilds a provider tool on replay by calling `provider.tools()` with the stored context, so the gate holds when a step replays. The alternatives do not fit: `agent/tools/file.ts` exporting `disableTool()` removes the tools on every turn, and a scope resolver has one answer per turn, not one per operation. Recalled memory reaches the model as a user-role message, and the model treated a recalled block that read like instructions as data, which is the posture `agent/instructions.md` asks for.

**The CLI runs on Node, not on Bun, and refuses anything below 24.** Invoking it through `bun run` does not change that, so CI needs `actions/setup-node` alongside `setup-bun`.

**eve 0.62 needs `ai` >= 7.0.105, and an `overrides` floor can hold it below that (2026-09-19).** `ai` is a peer dependency, so nothing fails at install: discovery dies later with `The requested module 'ai' does not provide an export named 'experimental_evaluate'`, blamed on whichever authored module loaded first, which here was the GitHub extension's tool file rather than anything at fault. `package.json` carried `overrides.ai: "^7.0.38"`, and `bun add ai@latest` kept resolving 7.0.97 under it while npm had 7.0.107. Raising the override to `^7.0.105` and deleting `bun.lock` fixed it. Read the peer range off `node_modules/eve/package.json`, not the changelog.

**eve 0.63.0 does not mount `@github-tools/eve-extension` 0.7.2 (2026-09-19).** `eve info` fails with `Selected module binding "extensions/github.ts" has no compile or runtime usage`, from the compiler's module-lifecycle check: the mount is discovered but neither compile-loaded nor reachable as a runtime entry. The extension was published 2026-09-19 10:44 and eve 0.63.0 at 16:38 the same day, so it predates the release. 0.62.0 mounts it and validates with no diagnostics, and 0.62.0 is where the autoevals removal landed, so it is the version to sit on until the extension ships against 0.63.

**eve does not load `.env` during discovery.** `eve info` and `eve build` read the process environment only; the README shows the `env $(...)` form. `vercel env pull` writes `GITHUB_WEBHOOK_SECRET` to `.env.local`, so a discovery run needs both files.

## GitHub

**The App's slug is what the code needs, not its display name.** The slug is both the handle people mention and the stem of the `[bot]` login the self-comment guard compares against. `baymi` was taken, hence `baymiai`, and the line in `agent/instructions.md` telling the model both names are it.

**Webhooks go straight from the App, not through Connect's forwarder.** Forwarding is metered per delivery and the events are identical either way. `connectGitHubCredentials` returns a `webhookVerifier` for the forwarder's signature, and eve skips the `webhookSecret` path whenever a verifier is present, so `agent/lib/github/credentials.ts` drops the verifier and supplies the App's own secret.

**`defaultGitHubAuth` stamps the repository and pull request number on `attributes`.** `repository` is `owner/repo` and `pull_request_number` is a string, empty on an issue session. `pullRequestFromAuth` reads them, which is how the check-in tool knows which pull request it is on without taking a target from the model.

**A tool set is priced per turn.** Every tool in the prompt on every turn costs tokens, and the `maintainer` preset alone is 79 of them; this agent mounts 19 GitHub tools, 11 of them on a review turn, and 8 of its own on a review. The reliability half of this note used to say that 42% of turns made zero tool calls at 18 or more tools against 5% at one to three, measured 2026-09-03. The gateway's own request log does not support that: over 14 days, zero-call turns run 24.2% at 1-5 tools and 15.4% at 18-29. The 2026-09-03 figure was collected while requests ran concurrently, which is the confound described below. Keep the list short for the tokens. A short list does not make the turn more reliable.

**GitHub's dependency graph does not read `bun.lock`, and on most of these repositories it is off (2026-10-02).** `GET /dependency-graph/sbom` answered 404 on nine of the ten installed repositories, and `/dependency-graph/compare` answered 403 on `baymi`. On `logixlysia`, the one where it answered, the SBOM listed only `package.json` entries with their ranges, such as `pkg:npm/vitest@%5E5.0.1`, and none of the 1,376 packages its `bun.lock` installs. Both readers went to the root `bun.lock` or `package-lock.json` first (`agent/lib/github/lockfile.ts`); remediation, which read it at the base commit, is gone, and `list_dependency_changes` compares it at the pull request's base and head, and asks the global advisory database about what was added, a hundred packages per call (`readAdvisoriesForPackages`). GitHub's own comparison is the fallback for projects without one. Run against `pigo#43`, the lockfile comparison found 84 added packages, among them `undici@7.29.0`, which has published advisories. Read with that, the same day, eight of the ten repositories had packages with published advisories.

**One advisory can carry a range per release line, each with its own patch (2026-10-02).** `GHSA-pmjh-fq2x-6v4x` lists `undici` twice: `>= 7.11.0, < 7.29.1` patched in 7.29.1, and `>= 8.0.0, < 8.10.2` patched in 8.10.2. The first version of `readAdvisories` took the first entry whose package name matched, and resolved `undici` 8.9.0 on `baymi` to a "fix" of 7.29.1, a downgrade. It now takes the entry whose range holds the version in use (`isInRange`), and `upgradeTarget` refuses any target that is not newer than every version in use. Run the resolver against a real repository after changing it. The unit tests passed with the bug in place, because every fixture had one range.

**`getPullRequestContext` is the one-call read.** It returns the pull request, its metadata and recent comments together; `listPullRequestFiles` adds the patches. On a GitHub turn neither is needed for the pull request under review, since the diff is already in context and the code is in the checkout.

**The eight CI tools cost about 2,000 tokens a turn, and the extension cannot leave them out of one (2026-10-23).** On `eve dev`, over the HTTP route, the same one-line question took 7,960 input tokens with all 19 GitHub tools offered and 5,899 with the eight CI ones withheld, a difference of 2,061 on `moonshotai/kimi-k2.7-code`. The Claude tokenizer reads the same tool block as 4,595 tokens for the original 11 and 7,679 for all 19 (`POST /v1/messages/count_tokens`, `claude-sonnet-5-5`), 3,084 more. The extension resolves its `include` at `step.started` with nothing from the turn to branch on, and an approval policy runs when the model calls a tool, which is after the tool has been paid for in the prompt. What eve does allow is replacing a mounted contribution: `agent/extensions/github/tools/github.ts` takes the extension's own resolver (`github` from `@github-tools/eve-extension/tools`), calls it, and drops the CI tools from the result unless `toolsForTurn` finds the turn's class is `maintainer`, `collaborator` or `app`. The tools, their policies and their durable callbacks are the extension's, untouched. Verified on a scratch copy with the cut keyed on the `local-dev` principal: the tool list in the reply went from 21 names to 13 and the input from 7,960 to 5,899 tokens. Not verified with a real `github:baymiai` turn, which needs a signed webhook and opens a check run on a real pull request; `toolsForTurn` is tested with the reviewer fixture. The cut is an allowlist over `classifyPrincipal`, so the reviewer, a stranger and a turn with no principal get the original eleven, and it never asks `isUnattended`, which is true for the app's own scheduled and CI turns, and those are the turns that read CI.

**`searchIssues` reaches past the installation, and nothing after it does (2026-10-23).** `author:PunGrumpy is:pr is:open draft:false updated:>=2026-09-23` returned 21 pull requests, the same 21 non-draft ones `gh search prs` finds with PunGrumpy's own token. One of them is `veggiemonk/awesome-docker#1573`, a public repository the App is not installed on (`list_installed_repositories` names 13, all PunGrumpy's). `listWorkflowRuns` on that repository answered too, since an installation token reads public data. So the lead sees upstream contributions in a search unless the query says `user:PunGrumpy`, and everything it could do there is a read: the check and workflow webhooks only arrive from installed repositories, and a write would be refused. Whether the search returns a private repository the App is not installed on was not tested; no such repository has an open pull request by PunGrumpy, since the two result sets match.

**GitHub lists only open pull requests on a workflow run (2026-10-23).** Run `39823444170` of open `baymi#52` carries `pull_requests: [{number: 52, ...}]`. Three failed runs on branches whose pull requests have since merged (`logixlysia#503`, `logixlysia#510`, `vecstore-sdk#53`) carry `[]`, and so does a push to `main` (`pigo`, `baymi`). A fork's pull request carries none either. The rerun guard (`agent/lib/github/rerun.ts`) has nothing to compare a head against for any of them and refuses: "attached to no open pull request".

**The rerun guard trusts GitHub's attempt count, and two things about it are unmeasured (2026-10-23).** `run_attempt` is read on every call, so a turn delivered twice finds attempt 2 the second time and is refused. Nothing here has seen a real rerun: no open pull request had a failed run, and a rerun on a real repository was out of bounds, so the claim that GitHub reports attempt 2 as soon as it accepts a rerun rests on its documentation. Two calls racing before that happens are not covered, and neither is a step replayed after GitHub accepted the rerun but before eve recorded it, if eve does not ask the policy again on replay. The installation token reads runs, jobs and job logs (`x-accepted-github-permissions: actions=read`, 200); whether the App has `actions: write` is unverified, and the rerun answers 403 if it does not. Who may rerun is a class table in `agent/lib/github/approval.ts`: the maintainer and the app, not a collaborator, the reviewer or a stranger. The HTTP route's principal is `local-dev` with type `local-dev`, which the classifier calls the maintainer, and the policy refuses it by its authenticator and type because `eve eval` runs as `local-dev`, so `eve dev` and the evals cannot reach an allowed rerun; the guard was run with a `user` fixture and the real installation token against two successful runs, and refused both with "ended success".

**What a CI webhook carries, and who it says sent it (2026-10-23).** For `workflow_run` and `check_run`, eve hands the hook `raw` as the event's own object (`payload.workflow_run`, `payload.check_run`), not the envelope, with `action`, `conclusion`, `headSha` and `pullRequests` (numbers only) normalized beside it. `run_attempt` and the workflow's `name` are in `raw`; a check run's `name` and `output.summary` are in `raw` too; a check run from Actions has `app.slug` `github-actions`, and every `workflow_run` is given that slug. `pull_requests` lists open pull requests on the same repository only, so a fork's run, a push and a merged pull request's run arrive with none, and eve then refuses the dispatch. `defaultGitHubAuth` names the event's sender, not the app, so a CI hook that returned it would run as whoever pushed. `chaseAuth` (`agent/lib/github/ci/turn.ts`) builds the `eve:app` principal instead, keeps the repository and pull request attributes the tools read, and adds the `ci_*` facts the end of the turn needs; `classifyPrincipal` reads it as `app`.

**A CI turn runs in a task-mode session of its own, because a mode only counts when a session is created (2026-10-23).** eve's GitHub dispatch sends every turn to `repo:<id>:pull:<number>`, the address the review and a mention use, and passes no `mode`. `channel-address.js` creates a session in `mode ?? "conversation"` with `requestInput: true` unless the mode is `task`, and a delivery to a session that is already live keeps that session's mode. So a chase joined the review's conversation-mode session: it was offered `ask_question`, eve's built-in `input.requested` handler posted the question as a comment on the pull request and parked the session, and `session.failed`, which receives no auth, judged a dead chase by the review's or the mention's state. `withChaseSessions` (`agent/lib/github/ci/session.ts`) wraps the webhook route's `from`, which is public (`Channel.routes`, `RouteHandlerArgs.from`), so an app send goes to the pull request's address plus the chase key, with `mode: "task"`; everyone else keeps the pull request's session. A task-mode session has no `requestInput`, so `ask_question` is not offered, and a turn that tries to park throws `Task mode cannot wait for follow-up input` and fails. A finished task turn still emits `turn.completed`, then `session.completed` (`emitTurnEpilogue`), so the chase settles where it did. The channel also replaces `input.requested`: the app's question is dropped and logged, and a person's is rendered the way eve's default renders it. `turn.failed`, which has the auth, tells Slack for the app and marks the channel state (`baymiFailedTurn`, cleared at `turn.completed`), and `session.failed` reads the mark first, so an app turn that dies in any session, one a mention or a review opened included, posts no notice and leaves the review's check run alone. The GitHub fragment (`agent/instructions/github.ts`) still tells a CI turn its reply is the comment; the chase brief overrides it in the same turn, and the channel discards the reply.

**The GitHub channel queues, it does not steer (2026-10-23).** eve's default `turnPolicy` is `steer`: a message that arrives while a turn runs continues that turn, and `turn-step.js` applies the newcomer's auth to it. On a pull request's session, a mention during a review took over the review's turn and its reply went out as the mention's answer, and a chase in the same session (before it had its own) would have swapped the review's auth for the app's and dropped the review's reply, leaving its check run `in_progress`. With `turnPolicy: "queue"` each turn finishes first. Queued messages fold into one turn only when their whole auth matches, so a burst of pushes is still one follow-up review, and a mention waits for the review in progress. The cost is latency: a mention during a long review is answered after it.

**A chase turn is settled at `turn.completed`, not `message.completed` (2026-10-23).** A model can end a turn that used tools without a closing message, and `message.completed` is skipped for an empty one, so settling there would leave a blocked pull request unannounced. `turn.completed` has no built-in handler to replace and fires once per turn. The chase learns whether its rerun happened from two witnesses: the run's `run_attempt` on GitHub, and the turn's own call of `github__rerunWorkflowRun` that completed without an error (`createRerunRecord`). That record is keyed by the chase, the run and the attempt: the run comes from the call's input at `actions.requested`, and the call is joined to its `action.result` by call id within the session, since a model's call ids repeat across sessions too. It was keyed by eve's turn id first, which is `turn_<n>` and unique only within a session, so one pull request's rerun silenced another's line. Whether GitHub reports attempt 2 the moment it accepts a rerun is still unmeasured, because no live rerun was allowed; with either witness the line stays silent, and with neither it says the rerun was not done.

**The chase's Slack line is keyed in Slack, the way the digest is (2026-10-23).** eve gives the app no store it may write, but a Slack post can carry its own key: `postKeyedText` puts it in the message's `metadata`, and `hasKeyedMessage` reads `conversations.history` back for it (`agent/lib/slack/messages.ts`, the digest's store, cherry-picked from #56 unchanged). That needs the history scope for the conversation's kind (`channels:history`) and `metadata.message:read`, which the bot already holds, as L4 measured; an earlier version of this note said a search needed scopes the connector lacks, which was true of `search.messages` and not of history. The bot must be a member of the notify channel, which the digest needs too. `sendLineOnce` (`agent/lib/github/ci/deliver.ts`) tags the line with `event_type` `baymi_ci` and the chase key, `owner/repo#run<id>@<attempt>` (the check run id for another app's check, `failed:<key>` for a chase that died, `failed:<session>` for a chase session that died with no turn failure), and looks three days back, as long as GitHub keeps a delivery for a manual redelivery. It fails closed: a history it cannot read posts nothing, and the morning digest carries the pull request. The in-memory ledger (`agent/lib/github/ci/ledger.ts`) still claims the key first, which catches two deliveries on one instance; across instances only the lookup does, and two that look at the same moment can both post. Starting a turn is still claimed in memory only, so a redelivery on a cold instance runs a second turn: its rerun is refused because GitHub reports attempt 2, and its line finds the first one and is dropped.

**Which red checks start a chase, and why those (2026-10-23).** A `workflow_run` is the right moment: the run has finished, every failed job has a log, and `rerun` accepts it. An Actions `check_run` fires per job while the run is still going, so it would start one turn per failed job on a run the rerun guard refuses until it ends; it is skipped. A `check_run` from another app (GitGuardian, a coverage service) has no log and no rerun, and is reported as such. Vercel's failing preview is a commit _status_, not a check run, and the channel parses neither `status` nor `pull_request_review`, so it starts nothing. GitHub reports a job that ran past `timeout-minutes` as `cancelled`, which a newer push also does, so a cancelled run starts a turn only when its log says `exceeded the maximum execution time`; unmeasured against a real timeout, because none exists on the repositories checked.

**The grounding ledger is keyed by session and turn, and never noted for the app (2026-10-23).** eve numbers turns from `turn_0` in every session, and a CI chase runs in a session of its own (`#lib/github/ci/session`), so its one turn is always `turn_0`, the id of a review's first turn. The ledger was keyed by the bare turn id: the L5b verifier showed a review that read nothing and answered at step 1 held back when nothing ran before it, and posted after an unrelated chase settled one tool result. The key is `${session id}:${turn id}` (`TurnKey` in `#lib/github/grounding`), used by `note`, `isGrounded` and `reportOnce`, so one session's failure card no longer swallows another's. The channel also skips `note` when the caller is the app: a chase's tool calls say nothing about whether a review read the code, even in a session they share. `trace.test.ts` reproduces the probe against the real handlers.

**A chase turn opens a sandbox it never uses (2026-10-23).** The built-in `turn.started` checks the repository out into the sandbox before the first model call, and a handler of ours would replace it for every turn, review included. So a chase costs a sandbox as a review does, and `message.completed` releases it the same way. With Vercel's snapshot quota spent (gate E1) the checkout and the release both answer 402; the chase finishes regardless, since the checkout failure is swallowed and the Slack line is sent before the release. Nothing on the chase's path reads the checkout. Against the Hobby quotas, one chase's sandbox costs about 0.05 GB-hours of memory and 10 to 30 seconds of active CPU for the clone, and active CPU (5 hours a month, shared with the reviews) is the one that binds. Skipping it means replacing `turn.started` for every turn and reimplementing eve's checkout, which eve does not export, so it stays: follow-up F9. A chase's session of its own changes nothing here, since the review's session deletes its sandbox after every turn as well.

**Log text that looked like a failure and was not (2026-10-23).** Run `39357357013` of `logixlysia` (`Typecheck`, 2026-10-20) printed `fail-on-cache-miss: false`, an action's input, far above its compiler error `configuration.mdx#21 (line 297): TS2304 Cannot find name 'token'.` The first classifier took the input as the evidence line and read `configuration.mdx` as `configuration.md` plus an `x`. Now `FAIL` is matched in upper case only, the wrapper lines every failed step ends with (`exited with code 1`, `Failed: docs#typecheck`, `ERROR command … exited (1)`) are skipped, and a file extension ends at a word boundary. That log is a fixture in `classify.test.ts`.

**A failure outside the diff is not a stale base by itself (2026-10-23).** A pull request's checks run on `refs/pull/<n>/merge`, the head merged into the base as it was when the run started, so a file the diff never touched failing there either broke on something the diff changed, such as an export it renamed, or fails on the base too. A rebase fixes neither. `assessCiFailure` reads the base branch's latest completed run of the same workflow (`workflow_id` from the run, `branch=<base ref>`, `exclude_pull_requests=true`, one run) and that run's jobs: the same job failed there is `stale-base`, a run or job that passed makes it the diff's own code (`breaks-caller`), and a base it cannot read leaves the failure `unknown` instead of guessing. The same read decides a network error in a test the diff changed, which is the diff's own code unless the base fails that job too: a diff can break the service its own test connects to. Only the last failing step is classified, from the `##[group]Run` the last `##[error]` sits under through that annotation, and a network line printed as `##[warning]`, as a warning or as a retry does not count, so an install step's retried `ECONNRESET` no longer turns a later type error into a flake. A run cancelled for any reason but GitHub's timeout is skipped, whatever else its log printed, and the pull request's files are read page by page up to GitHub's 3,000.

**A dev session outlives a change of sandbox backend, and selecting `just-bash` edits `package.json` (2026-10-23).** A pull request's session is durable: after swapping `docker()` or `justbash()` into `agent/sandbox.ts` to get around the 402, a webhook for a pull request that already had a session resumed that session on the backend it opened with (`waiting for sandbox template prewarm to finish`, minutes, no output), and only a pull request with no session started on the new one. And `eve dev` installed `just-bash` into `package.json` and `bun.lock` the first time it was selected; revert both before committing. Docker did not get through the checkout of a fresh session within seven minutes either; `just-bash` fails the checkout at once (swallowed) and the turn runs.

**`eve dev` reads `.env` over the shell, so unsetting a variable there does not unset it (2026-10-23).** A live check that exported `SLACK_NOTIFY_CHANNEL=""` before `eve dev` still posted to the maintainer's Slack, because the copied `.env` held the real value and `eve dev` loaded it. Remove the line from the copy.

**Only a workflow tool can call a hidden subagent, and it must not share the subagent's name (2026-10-23).** A subagent with `tool: false` is reached through `ctx.agent(name, ...)`, which exists only on a workflow tool's context (`defineWorkflowTool`, `"use workflow"`); an ordinary or dynamic tool's `ToolContext` has no `agent`, and a workflow body cannot come from a `defineDynamic` resolver. So the chase's gate is a static workflow tool whose approval policy refuses the classes it does not admit, not a tool whose presence is resolved per caller. eve's docs say `tool: false` lets an authored tool of the same name wrap the subagent; eve 0.62.0's `eve info` instead fails with `tool and subagent public name "chase" is shared by tool and local agent`, so the tool is `chase_pull_request`. A step in a workflow tool has to be an `async function` declaration with `"use step"`, which the lint's `func-style` rule is told to allow there.

**`git add` exits 1 when a pathspec names a path `.gitignore` already ignores, and a `&&` chain then prints nothing (2026-10-23).** Remediation's workspace commands staged with `git add -A -- . ':(exclude)node_modules' ':(exclude)**/node_modules'`. Before the install there is no `node_modules`, so the baseline commit worked. After it, git answers `The following paths are ignored by one of your .gitignore files: node_modules` and exits 1, so the digest, the change list and the modes chained after it all printed nothing, and exited 0 where a pipe hid it. The first two live chases fixed the test, passed every check, and then `push_fix` found "Nothing changed" three and four times; worse, the digest before and after was the same empty hash, so a verdict could have passed on a change nobody measured. Reproduced in the eve Docker image with a bare repository. The excluded paths now go in the checkout's own `.git/info/exclude` and the commands stage with a plain `git add -A`; `push_fix` refuses when a listing command fails, and an empty digest is never a verified one. Remediation never ran, which is how the bug outlived it. The `-z` listings also travel as base64 (`decodeListing`): command output reaches the runtime as text through two backends' transports, and the encoding takes NUL bytes out of that question; whether either backend drops them was not tested.

**An installation token's `permissions` on `GET /repos` says nothing about the App (2026-10-23).** For `PunGrumpy/baymi`, where the App has Contents write and later pushed, the field read `{"admin":false,"maintain":false,"push":false,"triage":false,"pull":false}`, pull included. It describes a person, and a token minted for an installation is none. The third live chase refused to push on it. Whether the App may write is known only from GitHub's answer to the write: the chase plans the push from the branch and its protection and reads a 403 on the fast-forward as no write access.

**Where the chase's budget lives (2026-10-23).** The ledger of today's chases and chased heads (`agent/lib/chase/budget.ts`) is in the runtime's memory, the same choice the CI ledger made, for the same reason: eve gives the app no store it may write. Memory is read-only for the app by design, `defineState` is per session while the cap is per day, eve exposes no Blob helper, and a Slack keyed message, the digest's store, would be a ping per chase. A GitHub check run on the head was the other candidate, but no API lists check runs across repositories by day. What memory loses on a cold start is the count: a fresh runtime allows three more chases that day and does not know a head was chased. Two things bound that. The per-run ledger in front of it (`agent/lib/github/ci/ledger.ts`) is in memory too, so it is the same gap, not a new one. And the rule that matters most for cost, that the app never chases a head that is its own fix gone red again, reads the head commit's author from GitHub on every claim, so a fix-fail-fix loop stops after one round even across cold starts; when GitHub will not say who made the head, the app does not chase. The store sits behind an interface whose `claim` throws when it cannot answer, and a throw refuses the chase. A durable store (Blob, an Upstash memory slot) is a change to that one file.

**The chase's bounds are enforced in code, and what stays unbounded is written down (C1b, 2026-10-23).** The verifier of C1 found that the chase's central claim, that it never touches a branch it was not handed, was only a sentence in the docs. `prepare_checkout` takes the repository, the pull request and the head as the model's own arguments, so a model talked into other values moved the chase to a pull request that never went through the gate. The auth already carries the anchor (the child session runs under the parent's auth, which the signed webhook stamped), so `bindingProblem` (`agent/lib/chase/bind.ts`) holds every class to it in the gate, in `prepare_checkout` and again in `push_fix`, and a mismatch ends the chase as `refused`. A turn with no pull request behind it, a Slack message or an issue comment, admits no chase: there is no signed anchor to hold the model's words to, and the alternatives, a signed admission token or an approval card, are not built. The same review found a branch name that was not percent-encoded in the fast-forward URL (a head named `main#x` addressed `main`), a result record keyed by the bare `turn_N` (pull request B's first turn read A's `pushed`), symlinks pushed as regular files, and files the project's checks rewrote absorbed into the "verified" digest from the second run on. Each is fixed with a test; `docs/chase.md` lists what is bounded and what is not.

**The budget counters stay in memory, and the own-fix refusal is the lasting guard (C1b).** Three chases a UTC day and one per head (`agent/lib/chase/budget.ts`) live in the runtime's memory, so a cold start or a second instance forgets them and allows three more. This unit does not build a durable store; the interface in `budget.ts` is where one goes. What bounds a loop across cold starts is the rule that the app never chases a head whose commit the App authored, read from GitHub on every claim. It now fails closed on an author GitHub cannot name: `commits/<sha>` answers `author: null` for a commit whose email is linked to no account, and that used to compare as "not ours".

**Three tree ids replace the change digest, and git's `write-tree` is the digest (C1b).** `git add -A && git write-tree` prints the tree id of everything tracked or not ignored; equal ids are the same files, modes and bytes. A is the baseline commit's tree, B the tree just before a run, C the tree after it. `git diff-tree -r --name-status -z B C` names what a run rewrote, so a rewrite stops the chase with the paths. The ids come from the sandbox, where the project's code runs, so a 40-hex check stands between them and the shell. A tree id covers a symlink as its link text, which is why symlinks are refused rather than hashed. The install is frozen (`--frozen-lockfile`, `npm ci`, Yarn `--immutable`): a project whose lockfile is stale on the head now fails the install and the chase reports it, which is the correct reading of a red CI that says "lockfile out of date" and not something a chase should paper over by committing a regenerated lockfile.

**The write probe is a blob (C1b).** The installation token's `permissions` read all false, so write access is learned by trying: `POST /git/blobs` with 18 fixed bytes answers 201 for Contents write and 403 or 404 for read. It runs in the gate, before the budget claim, so a read-only repository costs no slot and no sandbox. The blob is unreferenced and GitHub drops it; the same bytes are the same object.

## Configuration

**`imports` wildcards in `package.json` are literal substitutions.** `#*` mapped to `./agent/*` does no extension resolution, which is why the map includes the `.js` suffix (`"#*": "./agent/*.js"`) so call sites read as `#lib/env`.

**`emptyStringAsUndefined: true` makes `VAR=""` unset, not empty.** A required variable with an empty value fails discovery as "missing" rather than as a validation error, and `.env.example` placeholders written as `""` are only runnable for the optional block.

## Evals

**The HTTP route is the maintainer to the trust model and nobody in particular to the model (2026-10-23).** `localDev()` gives every eval `local-dev`, which `classifyPrincipal` reads as the maintainer (memory write, remediation, the CI tools). The prompt never carries the class, so the model decides who it is talking to from the words. `lead/replies-in-thai-to-owner` therefore opens as "It's PunGrumpy." and expects Thai, and opens a second session with no name and expects English. `merge #101 now`, from the same maintainer by trust, got English on both runs. A real Slack turn from the owner cannot be driven from `eve eval`; the Slack fragment ("You are talking to the person you work for") is loaded on the HTTP route too, and was not enough to make the model answer an unnamed caller in Thai.

**Development memory is one in-process store that every session shares (2026-10-23).** `fileMemory()` picks Vercel Blob when `VERCEL` is set and an in-memory backend, a module-level singleton, when it is not and the process is `eve dev`. `vercel env pull` writes `EVE_MEMORY_BLOB_STORE_ID` into `.env.local`, but nothing reads it without `VERCEL`, so a local run never touches the production document. A preference told in one session is recalled in the next: in `lead/remembers-a-preference`, session `wrun_01M5JGQBWB8H12P3K5PJJHCRV3` told it ("Got it. Saving that now." then `file__save_memory`) and session `wrun_01M5JGQVT3ZC2B3V58431QXX4Q` answered "during ship week, the week before a release, you want the digest to list blockers only" with no tool call. The store outlives the session, so the eval ends by asking Baymi to forget it (`file__remove_memory`, tracked, not gated). On a deployment the same eval would write PunGrumpy's real memory, because a Vercel OIDC user is a maintainer, so it skips unless `/eve/v1/info` reports `mode: development`.

**The preference the brief names was already in the instructions, and the model once promised to save without saving (2026-10-23).** "Release pull requests from changesets are healthy unless CI fails" is in the `engineering-lead` skill, so a reply that repeated it would not show that memory worked; the eval uses one nothing else holds ("ship week"). In the first run the model reasoned "I should save this to memory", answered "Got it. I will remember that…", and called no tool; a new session said it had nothing stored. The gate on `file__save_memory` exists for that: a claim to remember with no save is a failure the reply alone hides. The second run saved. One miss in two on `moonshotai/kimi-k2.7-code`.

**A quiet digest comes back as a sentence and a line of counts, and one reply in three lists every healthy pull request (2026-10-23).** `lead.ts` says "when nothing needs attention, say so in one sentence and stop"; the skill's digest ends with "one line of counts for the rest". Kimi follows the skill: a sentence and "4 อันปกติ, 1 อันเป็น release PR" in two of three calibration samples, and in the third it wrote the whole list with links. With a row marked "Baymi review pending" it named that pull request in the first run, which the orders call a number, not a line. `lead/quiet-when-healthy` allows the sentence and one line of counts, gates on naming no pull request, and leaves the choice between "one sentence" and "a line of counts" to whoever settles the orders.

**`merge` is checked in two places because the GitHub extension hides its tools (2026-10-23).** `/eve/v1/info` lists `github__github` as one dynamic tool, so the names behind it are not in the report. `lead/never-merges` checks the `GITHUB_TOOLS` list the extension is mounted with and the tool names `/eve/v1/info` does report, and then asserts no `actions.requested` event names a merge-like tool. Adding a merge tool fails the first two before a model is asked. Mounting one on purpose means changing this eval in the same pull request.

**`eve eval` refuses to boot while `eve dev` runs for the same app, and the gateway's 5 requests a minute still applies (2026-10-23).** "A dev server is already running for this eve agent": stop it, or pass `--url`. `review/finding-format` followed straight by `safety/ignores-injected-instructions` hit `GatewayRateLimitError` on the second. The runs here used `--url` for the `lead` evals and a self-booted server for the three existing ones, and the rate-limited eval passed on its own.

## Deployment

**Vercel Deployment Protection answers before the app does.** Every route on a protected preview returns 401 or a redirect to Vercel SSO, including the webhook paths, so GitHub and Slack cannot reach a protected preview at all: point the webhooks at production.

**`ai.model` is empty unless the hook is told the model.** evlog reads the model from the id eve reports at `session.started`, and with a static gateway id that still arrives empty: a turn on 2026-10-19 without the option logged `ai: 1 call` and no model. `agent/hooks/evlog.ts` passes `model: MODEL`. `ai.estimatedCost` stays empty because evlog computes it only from a `cost` map. The dashboards count tokens.

**PostHog has two hosts and they are not interchangeable.** `POSTHOG_HOST` is the _capture_ endpoint (`us.i.posthog.com`, note the `i`); the query endpoint is `us.posthog.com`. Posting events at the query host does not fail loudly enough to be obvious.
