# Architecture

## Project identification

- **Name:** Baymi (`baymi`), one person's engineering lead and security reviewer for their repositories, built on eve. On GitHub it answers as the `baymiai` App, since `baymi` was already registered
- **Maintainer:** PunGrumpy
- **License:** MIT
- **Last updated:** 2026-10-23

## Overview

Baymi watches the repositories its GitHub App is installed on. When a pull request opens on one of them, it reads the diff and the checkout and posts one security review as a comment. When the maintainer mentions it on an issue or pull request, it answers there. In Slack it answers the maintainer about those repositories, remembers how the maintainer likes things done, and posts on its own, once and briefly, when a review finds something that should not wait.

Baymi is also PunGrumpy's engineering lead. Its standing orders are a fragment, `agent/instructions/lead.ts`, that loads on every turn except an unattended review, and the playbook for chasing one pull request is the `engineering-lead` skill: triage conflicts, then review threads, then CI; classify a failing check as a flake, a stale base, or the diff's own code; speak to PunGrumpy only for what needs them; leave every merge to them. Today it does this when asked, in Slack or on a mention, with the GitHub tools it already has. The tools that read CI results, the weekday digest schedule, and a sandboxed chase subagent are separate changes, so the instructions describe what they do and name none of them.

The reviewing agent never changes a repository and never runs its code. Every write beyond its reply either runs because a trusted person asked or waits on an approval card. The one exception is the chase: when a pull request's own code fails its checks, the `chase` subagent reproduces the failure in a sandbox of its own, fixes it, and pushes the fix to that pull request's branch. The CI turn hands it over for the maintainer's own pull requests, and the maintainer can ask for one; nobody else can start it.

eve discovers every capability from the filesystem under `agent/`. There is no central registry or wiring file: a tool's name is its filename, a memory slot's name is its filename, and so on.

## Why it is read-only

The sandbox holds a checkout of whatever pull request last opened, and the pull request came from whoever opened it. eve attaches the installation token to the sandbox's outbound requests to `github.com` for the checkout. A shell that could run the pull request's code could make requests from inside that boundary. So `agent/agent.ts` sets `defaultTools: false`, which removes `bash` and `write_file`, and with them `web_fetch` and `web_search`, because a URL built from an untrusted diff could send a private repository's contents to an outside host in the query string. `agent/tools/` adds back `read_file`, `load_skill`, and `ask_question`, and opts into `glob` and `grep`, which search the filesystem. The review is reasoning over code, and the instructions say so. The agent never claims to have run, tested, or reproduced anything.

The chase subagent is the one place with a shell, and it sits outside this agent on purpose. A declared subagent inherits none of the root's tools or sandbox. Its sandbox holds no credential and reaches only the npm registries; the runtime downloads the pull request's head and pushes the fix through the API itself. It only ever holds the head of a pull request the maintainer owns or asked about, never a fork's, at a commit read from GitHub. The tool that starts it refuses the reviewer, so the review turn that reads a stranger's diff cannot call it. `docs/chase.md` describes the boundary.

`todo` and the built-in `agent` delegation stay off for a smaller reason: every tool in the prompt costs tokens on every turn (`docs/notes.md`), and a review is one pass with no side quests to track.

## Who is acting

`classifyPrincipal` in `agent/lib/trust.ts` is the only code that reads a principal's id, type or authenticator, and it puts every caller in one of five classes. The predicates callers use (`isUnattended`, `isReviewer`, `isApp`, `mayChase`) and the memory table (`memoryAccess`) are written over the classes, and the tables are exhaustive, so a new kind of caller does not compile until every table has a row for it.

| Class | Who | Attended | Memory | Chase |
| --- | --- | --- | --- | --- |
| `maintainer` | A person of the Slack workspace, the repository's owner on GitHub, or the operator at a terminal or in the Vercel team | yes | read and write | yes, except the `local-dev` terminal |
| `collaborator` | Another owner, member or collaborator the mention gate admitted | yes | none | no |
| `reviewer` | `github:baymiai`, the constructed principal on a stranger's pull request | no | none | no |
| `app` | `eve:app`, a `runtime` principal: a schedule fire, or a CI event the app starts itself | no | read only | only its own CI turn's own-code failure |
| `stranger` | No caller, a bot, a service, a Slack guest outside the pinned workspace | no | none | no |

`isUnattended` is true for the reviewer and the app. What is specific to a review (the review instructions, the one reply posted as a GitHub review, the check-in) asks `isReviewer`, so the app's turns never inherit it. GitHub writes that need a person (`agent/lib/github/approval.ts`) are refused on every unattended turn, so the app cannot comment, open an issue, merge or approve. The one write it may do is rerunning a failed workflow, which is not idempotent (each call starts another attempt) and so has a policy of its own on that tool: the class check, then a guard that reads the attempt from GitHub. The app principal is measured, not assumed: `docs/notes.md` has its shape.

## Data flow

1. **A pull request opens** on an installed repository. GitHub posts `pull_request` at `/eve/v1/github`; `shouldReviewPullRequest` accepts `opened`, `ready_for_review` and `synchronize` from a human, the channel opens the check run on the head commit, and it starts a session under the reviewer principal. eve injects the diff and checks the head commit out. The agent loads `security-review`, reads the diff and the surrounding code, and writes its reply in the skill's format. The channel submits that reply as a GitHub review, one inline comment per finding on its line, and posts the summary as one comment on the pull request. If a finding is critical or high it calls `notify_maintainer` once, and the maintainer gets one line in Slack with a link. Every later push runs the review again on the new head, with a new check run, edits the summary comment rather than adding one, and submits a review only for findings that are new.
2. **The maintainer mentions `@baymiai`** on that pull request, or any issue. `shouldDispatchComment` admits owners, members, and collaborators; the session (the same one, on a reviewed pull request) continues under their principal, so the uncarded writes are available and the review fragment is not. Memory is available when they are the maintainer. The channel posts the reply in the thread.
3. **The maintainer talks to Baymi in Slack.** A DM, a mention, or a reply in a thread it owns starts or resumes a session. It answers from the GitHub tools, remembers what it is told to keep, and points a request for a full review back at the pull request.
4. **A review dies, or never ran.** The channel's failure handler recognizes an unattended review from the state (a pull request with no triggering comment), logs the detail, posts nothing in the pull request's timeline, fails the check run so the author can see the change went unreviewed, and sends the review-failed line to Slack when a target is configured. An unattended reply with no tool loop behind it is held back the same way. Two things mark it: no `action.result`, and a `stepIndex` the loop never advanced.
5. **The maintainer asks for a chase.** A mention or a Slack message names a pull request whose checks fail. The root calls `chase_pull_request`, which admits the pull request and claims the budget, and the `chase` subagent reproduces the failure in its own sandbox, fixes it, runs the checks, and pushes to the pull request's branch or opens a pull request against it. The root reports the result.
6. **A check finishes red on a pull request.** GitHub posts `workflow_run` (or `check_run`, for another app's check) at `/eve/v1/github`. `startChase` skips a success, a run still going, Baymi's own check, a pull request that is closed, a draft, someone else's or already past the event's head, and any run it started a turn for already (the ledger keys on run and attempt). Otherwise it reads the failed jobs' logs (and the base branch's latest run of the same workflow) and starts a task-mode session of its own under the app principal, at the pull request's address plus the chase key, with the classification in its brief. The model reruns a flake once and hands the diff's own failure to `chase_pull_request` once; at `turn.completed` the channel reads the run's attempt back from GitHub (and its own record of the rerun call), decides whether anyone needs to hear (`decideSpeak`), and sends one line to Slack with the pull request link first, keyed in the message's metadata so a redelivery on another instance finds it and posts nothing. It posts nothing on the pull request. Production receives these events only after the App subscribes to `check_run` and `workflow_run` and holds Actions write (gate G3).

## Data stores

- **GitHub** (external): the repositories and pull requests. All access goes through the eve channel and `@github-tools/eve-extension` with an installation token brokered by Vercel Connect; no token in code.
- **Slack** (external): the maintainer's workspace. Inbound through the eve channel via Connect; the check-ins post with the same connector's app-scoped token.
- **Vercel Blob**: the memory document, under eve's file memory prefix, authenticated with the store's token or the project's OIDC. `eve integration setup file-memory` provisions it.
- **Vercel Sandbox**: the checkout the read tools search, and the chase's own sandbox, which `push_fix` and `stop_chase` delete when the chase ends. Neither is a durable store. The GitHub channel deletes it after a turn posts its reply, and the next turn gets a new sandbox with the head checked out again.

There is no application database.

## Deployment

The agent runs on Vercel, the same way locally (`eve dev`) and in production (`eve deploy`). The GitHub App's webhook URL and the Slack connector's trigger both point at the production deployment; a preview behind Deployment Protection cannot receive either (`docs/notes.md`). Which repositories the agent watches is decided by where the GitHub App is installed, and nowhere else.
